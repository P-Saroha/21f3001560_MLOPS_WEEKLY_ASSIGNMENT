============================================================
25. TASK 1 - ML SECURITY THREAT VECTORS
============================================================

DATA POISONING

Target stage:

Data ingestion / training.

Description:

An attacker modifies existing training samples or injects
incorrect samples into the training dataset.

Effect:

The model learns from corrupted information and its decision
boundary can change.

Our Week 8 experiment is a simulation of data poisoning.


ADVERSARIAL EXAMPLES

Target stage:

Inference.

Description:

An attacker creates a specially modified input that causes
the trained model to make an incorrect prediction.

Difference from poisoning:

Poisoning attacks training data.

Adversarial examples attack inference inputs.


MODEL EXTRACTION

Target stage:

Model serving / inference API.

Description:

An attacker repeatedly queries a deployed model and uses the
responses to reproduce or approximate its behaviour.

Possible mitigations:

- Authentication
- Rate limiting
- Query monitoring
- Restricting prediction information


PROMPT INJECTION

Target stage:

LLM inference/application layer.

Description:

A malicious instruction is included in user input or a
document and attempts to manipulate the LLM into ignoring
its intended instructions.

Possible effects:

- Unwanted actions
- Information disclosure
- Ignoring system instructions


============================================================
26. TASK 5 - DATA POISONING DETECTION
============================================================

Production systems should use multiple security and data
quality checks.

1. SCHEMA VALIDATION

Check:

- Required columns
- Data types
- Missing values
- Unexpected categories

2. STATISTICAL VALIDATION

Monitor:

- Mean
- Standard deviation
- Minimum/maximum
- Feature distributions
- Class distribution

3. ANOMALY DETECTION

Identify samples that are significantly different from normal
training data.

4. DATA PROVENANCE

Track:

- Source of the data
- Who generated it
- When it was created
- When it was modified

5. DATA VERSIONING

Use dataset versioning to identify unexpected changes and
allow rollback to known-good data.

6. DATA QUALITY GATES

Do not allow training to start when important quality checks
fail.

7. ACCESS CONTROL

Only authorized users and systems should be able to modify
training data.


============================================================
27. DATA QUANTITY VS DATA QUALITY
============================================================

More data does not automatically solve a poisoning problem.

Example:

If a dataset contains:

1000 total samples
20% poisoned

Then:

800 clean
200 poisoned

If more data is collected but the same contamination ratio
continues, the amount of poisoned data also increases.

The important quantity is the clean-data ratio:

Clean ratio =
clean samples / total samples


============================================================
28. CLEAN DATA RATIO
============================================================

If the clean-data ratio decreases, more total samples may be
required to obtain the same number of reliable clean samples.

However, collecting more data is not a sufficient mitigation
if the newly collected data is also poisoned.

The preferred production approach is:

Detect contamination
        ->
Remove or quarantine suspicious data
        ->
Validate remaining data
        ->
Train model
        ->
Monitor model performance


There is no single universal minimum clean-data ratio for all
ML problems.

The required amount of clean data depends on:

- Dataset size
- Model complexity
- Class balance
- Feature separability
- Noise level
- Required performance

============================================================
42. FINAL RESULTS / CONCLUSION
============================================================

The MLSecOps experiment demonstrated that:

1. ML systems have multiple security attack surfaces.

2. Data poisoning can degrade model performance.

3. Small random poisoning levels of 5% and 10% did not
   noticeably affect this particular IRIS experiment.

4. At 50% poisoning, performance degraded:

   Accuracy: 93.33% -> 90.00%
   F1:       93.33% -> 89.97%

5. The model remained far better than random guessing.

6. Data quality is more important than simply increasing
   the amount of data.

7. Production ML pipelines should use data validation,
   anomaly detection, provenance tracking, versioning,
   access control, and quality gates.
